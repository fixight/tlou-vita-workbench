# Стриминг чанков: результат расшифровки и контракт движка

Карточки игровых областей и назначение обработчиков C++: [TRIGGERS.md](TRIGGERS.md).

Готов выбор статических чанков по оригинальным областям и состоянию сюжета.
Результат для Остина: `D:\TLOUPS4\AustinStreaming`. В нём 15 мировых областей
стриминга, 426 областей вместе с игровыми/звуковыми, 149 callback-программ,
127 прямых ресурсов и зависимостей. Компактный `world-home.tltr` занимает 15 КБ.
Графы 18 глав извлечены одним парсером; в графе Остина 27 задач и 28 связей.

## Что вызывать

1. Один раз прочитать `World::Load("app0:/assets/metadata/world-home.tltr")`.
2. Создать `InitialHomeState()` из `HomeStory.h`; объект настроек должен быть
   действительно создан, как предполагает эта начальная конфигурация Остина.
3. Каждый кадр передавать мировую позицию камеры в `World::Select(position, query)`.
   Координаты Y вверх, метры, такие же, как в экспортируемых LVL5.
4. `Planner::Update(world, selection, readyResources)` вернёт `load/show/hide/release`.
   Индексы относятся к `world.levels`; запись содержит имя ресурса, файл чанка
   и зависимости. Передавать `description.file` в существующий
   `DataLoader::LoadLevel(...)`, сохраняя геометрию/коллизию с владельцем-чанком.
5. Загрузка должна сообщить готовность только после подготовки обязательных данных.
   Пока новый набор не готов, планировщик оставляет предыдущий видимым.
   `release` освобождает ресурс только после проверки ссылок других подсистем.

Полный пример границы подключения — `StreamingIntegrationExample.cpp`.
`Host` — точки подключения существующих загрузчика, рендера и владельцев ресурсов.
Данный пример ещё нужно связать с движком. Основной игровой цикл и его загрузчик
автоматически не заменялись.

`level.bin` в корне экспорта сохраняет прежний объединённый уровень.
Для стриминга используются **отдельные** файлы `assets/levels/*.bin` из TLTR.
`description.file` бывает пустым: это ресурс без экспортированной геометрии,
сценарный контейнер, кеш либо ещё не экспортированный чанк. Различие проверять
по `streaming_runtime.json`: манифест, исходные PAK, покрытие экспорта. Пустой
путь нельзя передавать в LoadLevel или автоматически считать готовым ресурсом.
Кеши удерживаются как зависимости, их геометрия не становится видимой автоматически.

## Состояние сюжета

Стример читает состояние, сценарный контроллер его меняет:

```cpp
streamer.BeginTask("hom-house-escape");
// После соответствующего игрового события / катсцены:
streamer.CompleteTask("hom-house-escape");
streamer.BeginTask("hom-road-suburbs-start");
streamer.SarahEnteredCar();
```

`before-task?` означает `!task-complete? && !task-active?`, а не сравнение
номеров задач. `task-complete?` и `task-active?` читают отдельные состояния.
Неизвестное состояние вызывает диагностическую ошибку.

Объект `0x69c85a6d` сопоставлен с `ss-hom-player-settings-1` из оригинального PAK.
Его boolean `0x4f12da44` имеет исходное значение false и устанавливается в true
обработчиком `sarah-car (on (start))`; тот же флаг устанавливает сценарий побега.
У API понятное имя `SetSarahCarStarted`, исходное имя свойства не восстановлено.
Это позволяет воспроизводить выбор полного/упрощённого интерьера без догадки
по расстоянию до дома.

`home_task_links.txt` содержит исходные связи задач; `trigger_rules.json` —
читаемые условия каждого варианта и точные списки ресурсов.
Задачи автоматически не завершаются при входе в области стриминга. Переходы
катсцен, интеракций, диалогов и акторов принадлежат сценарной логике.

## Что теперь доказано

* Вход / пребывание / выход: callback-ключи `1157c38c`, `f131b5e1`, `5b4bfb24`.
  В `eboot 809940..8099d0` enter/exit сопоставляются с исходными hash-строками.
* Несколько объёмов одной области объединяются. `80fe60..80fe73` продолжает
  список, пока не найдено попадание.
* Категория `camera`, исходная сетка и порядок кандидатов сохранены.
  После положительного выбора `79e6f4/79e732` выходит из поиска. Поэтому
  используется **первая** подходящая область, объединять все пересечения неверно.
* Плоскость берётся из третьего столбца `world_to_face_matrix`, включая
  смещение в четвёртой строке. У сериализованного `normal_raw.w` ноль.
* Сферы и ориентированные цилиндры читаются аналитически. Их сетки в Blender
  служат отображением; исходные параметры сохранены в JSON.
* Внутри набора дублирующий no-display снимает display; ресурсы всё равно нужны.
* Разрезы задач читаются по таблицам ID/указателей и проверяются по хешам имён.

Адреса — файловые смещения исследованного eboot. Дизассемблированная основа:
`output/eboot_streaming_runtime.asm`. Подтверждённая цепочка boolean описана
в `host_state_notes` итогового JSON.

## Blender и экспорт

Открыть `scene_native_streaming.blend` либо запустить
`D:\TLOUPS4\AustinStaticLighting\blender_native_streaming.py` в текущей сцене.
Скрипт обновит метаданные и инструменты, сохранит существующие меши и их трансформации.
Обновление также сохраняет видимые чанки, выбранный участок, сюжетный шаг,
настройки областей, положение игрока и состояние симуляции. Возврат к дому
не выполняется; запуск обычного `blender_streaming_tools.py` по-прежнему
инициализирует редактор, поэтому для обновления используйте updater.
В панели TLOU включить оригинальные правила выбора, выбрать активную задачу,
включить симуляцию и двигать `TLOU_PLAYER_PREVIEW`. Предыдущие задачи в этом
предпросмотре помечаются завершёнными, выбранная — активной. Это тестовый ввод
для настоящих селекторов, а не автоматическое проигрывание сценариев.

В панели Vita экспортировать **Все чанки**. По умолчанию выбран этот режим.
В обычной структуре экспорта появятся:

```text
level.bin
assets/models/...
assets/textures/...
assets/levels/<chunk>.bin
assets/metadata/world-home.tltr
assets/metadata/streaming_runtime.json
assets/metadata/streaming.bin
assets/metadata/level_files.json
assets/metadata/NativeStreaming.h
assets/metadata/HomeStory.h
assets/metadata/StreamingIntegrationExample.cpp
```

Изменённые объёмы переиндексируются консервативно с сохранением порядка
приоритета, доказанного оригинальными ячейками. Если порядок противоречив,
экспорт останавливается. Новые пересечения после ручного перемещения областей
являются результатом редакторских изменений.

## Границы результата

TLTR исполняет только инструкции селекторов статического стриминга. JSON
сохраняет игровые callback-программы и точные ID отправляемых событий; весь
сценарный VM, катсцены и акторы ещё не реализованы. Текущий C++ модуль принимает
runtime overrides от движка явно. Активационные группы неизвестного типа и
неизвестные инструкции других глав вызывают ошибку вместо выбора произвольного набора.

Предзагрузка и время старта чтения — настройки порта. Можно заранее вычислять
набор по прогнозируемой позиции камеры и ограничивать его бюджетом памяти.
Планировщик готовности не заменяет раннее чтение для медленного носителя.
Рендер, звук, акторы и коллизии должны иметь отдельные правила активности:
no-display сам по себе не означает, что весь ресурс перестал работать.

## Проверка

13 Python-проверок: исходные графы, ветви дома, отказ при нехватке состояния,
первая область, нулевой селектор, координаты сетки, сферы/цилиндры, циклы
зависимостей, строгие границы редактируемых объёмов и ожидание готовности.
Python и C++ совпали на 1232 сочетаниях исходных мировых позиций и сюжетного
состояния, затем на 1232 случаях после экспорта через Blender. Blender проверил обновление
реальной сцены без изменения трансформаций визуальных объектов и тестовый
экспорт двух отдельных LVL5 с точными app0-путями. Модуль компилируется VitaSDK;
прохождение Остина на реальной Vita не проверялось.
